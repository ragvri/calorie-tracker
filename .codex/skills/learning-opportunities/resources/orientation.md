# Repo Orientation: Calorie Tracker (CalPal)

> Generated by orient. Re-run to update.

## One-line purpose
A mobile-first web app that uses Google Gemini AI to analyze photos of food and log their estimated calories, protein, carbs, and fat — replacing manual food journaling with a single photo.

## Primary language(s)
Python

## Pipeline / workflow stages

1. **Photo capture** — User taps the FAB, takes or selects a food photo via a bottom-sheet form
2. **Image compression** — `image_utils.py` compresses the raw image to JPEG (max 800px width, quality 80) for efficient API transport
3. **AI analysis** — `gemini_client.py` sends the compressed image + optional user notes to Google Gemini Flash, which returns a structured `FoodAnalysis` (food name, calories, macros, confidence)
4. **Database persistence** — `main.py` saves the analysis result as a `FoodEntry` row in SQLite via SQLAlchemy
5. **HTMX partial update** — The response returns an `_entry_list.html` partial that HTMX swaps into the page, updating the daily summary ring and macro bars without a full reload
6. **Day navigation & delete** — Users browse history via a date strip (last 7 days) and delete entries with an HTMX-powered delete that returns the same partial

## Key files

- `app/main.py` — FastAPI app: all routes (index, upload, day view, delete) + helper functions | Central file — understand the request flow here first
- `app/models.py` — SQLAlchemy `FoodEntry` model: schema for the SQLite database | Defines what data is stored
- `app/gemini_client.py` — Gemini AI integration: sends images, parses JSON responses, fallback model chain | Core intelligence — read to understand prompt engineering and retry logic
- `app/schemas.py` — Pydantic models (`FoodAnalysis`, `FoodEntryResponse`, `DaySummary`) | Define the contract between AI output and the app
- `app/database.py` — SQLAlchemy engine, session factory, `DATA_DIR` logic | Infrastructure setup, Docker vs local path resolution
- `app/image_utils.py` — Image compression (resize, convert to RGB, JPEG save) | Runs before AI analysis — affects both speed and API cost
- `app/templates/base.html` — Jinja2 base template: Tailwind CSS + Inter font + HTMX 2.0, date strip, FAB, upload bottom sheet | All UI chrome lives here
- `app/templates/partials/_entry_list.html` — HTMX partial: daily summary card with calorie ring + macro bars + entry cards | The core UI payload swapped in/out
- `pyproject.toml` — Project metadata + dependencies (FastAPI, SQLAlchemy, google-genai, Pillow, etc.) | Entry point for running the app
- `Dockerfile` — Container build using `uv` Python image | How the app is deployed

## Core concepts

**HTMX-driven SPA**: The app uses HTMX 2.0 (no JavaScript framework) for dynamic updates. Upload, day navigation, and delete all return HTML partials (`_entry_list.html`) which HTMX swaps into the DOM. The `hx-target`, `hx-swap`, and `hx-trigger` attributes control behavior. There is no JSON API — the server returns rendered HTML fragments directly.

**Gemini structured output**: The `google-genai` SDK is called with `response_mime_type="application/json"` and `response_schema=FoodAnalysis` (a Pydantic model). This forces Gemini to return valid JSON matching the schema. The model falls back through a list of models (`gemini-3-flash-preview` → `gemini-2.0-flash` → `gemini-2.0-flash-lite`) with retry on rate limits (429). Temperature is set to 0.1 for consistent estimates.

**Single-table SQLite persistence**: All data lives in a single `food_entries` table with columns for date, time, food_name, calories, and macros (protein_g, carbs_g, fat_g). The `DATA_DIR` defaults to `<project>/data/` locally and `/app/data/` in Docker (configurable via `DATA_DIR` env var). Images are stored under `data/images/<YYYY-MM-DD>/<uuid>.jpg`.

**Conservative calorie estimation**: The Gemini prompt is engineered to always round up when uncertain ("When uncertain, use the HIGHER estimate") and account for hidden calories (oils, sauces, frying). This is explicitly stated as intentional — underestimation defeats weight tracking. Confidence levels (`high`/`medium`/`low`) flag uncertain results in the UI with a "rough" badge.

**Mobile-first UI**: Tailwind CSS with a custom brand/accent color palette, a fixed FAB for photo capture, a bottom-sheet upload overlay, a horizontal date strip (last 7 days), and a circular calorie progress ring. All styling is inline in `base.html` — no separate CSS file.

## Common gotchas

- **GEMINI_API_KEY required**: The app will crash at first upload with a `RuntimeError` if `GEMINI_API_KEY` is not set in the environment. Free tier has daily quota limits — 429 errors surface a user-friendly message in the UI. Check `gemini_client.py` line ~25.
- **IMAGES_DIR vs IMAGES_DIR path**: Images are saved to `DATA_DIR / "images"` (not `app/static/`), but the app mounts both `app/templates/static` (for app static files) and `DATA_DIR / "images"` (for user uploads) as separate FastAPI `StaticFiles` mounts. The `image_url` field in `_entry_to_dict()` constructs URLs with `/images/` prefix, which maps to the second mount. Don't confuse the two.
- **HTMX event timing**: The loading overlay is triggered by `htmx:beforeRequest` and hidden by `htmx:afterRequest` / `htmx:responseError`. If an event doesn't fire (e.g., network abort), the loading overlay stays visible. The overlay is controlled in `base.html` via a global event listener.
